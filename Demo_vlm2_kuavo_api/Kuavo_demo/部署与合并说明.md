# Kuavo 电梯门感知与进出功能合并部署说明

## 1. 合并思路

现有两个功能不需要合成一个 Python 进程，也不要让导航程序直接调用云端 API。保持两个程序独立，通过 ROS 话题连接：

```text
AAEON / 感知侧
头部相机 -> VLM 门状态识别
         -> /elevator/perception/state
                      |
                      v
机器人 / 控制侧
elevator_text_main.py -> 原有 NodeNavigationToTarget
                      -> 进入、转身、退出

控制侧 -> /elevator/perception/mode -> 感知侧
          door_monitor / idle
```

职责分工：

- 感知侧继续使用已经能单独运行的 `Demo_vlm2_kuavo_api`，只负责发布门状态，不发送运动命令。
- 控制侧继续使用已经验证过的 `api.NodeNavigationToTarget` 和 `api.NodeWaitForArrival`，不读取相机、不访问云端 API。
- 新的 `elevator_text_main.py` 是状态机，只在门状态满足条件后调用原导航节点。

完整流程：

```text
门外等待完整开门
  -> 调用已有导航进入轿厢，最终朝向设为面向门
  -> 等待门关闭
  -> 等待门再次完整打开
  -> 调用已有导航退出到门外原点
  -> 感知切换 idle
```

### 8.2 终端 B：在 AAEON 启动 VLM 感知

### 8.3 终端 C：在机器人侧检查跨机话题

先只看话题，不启动运动程序：

```bash
cd /home/lab/kuavo-ros-control
source devel/setup.bash
rostopic info /elevator/perception/state
rostopic echo -n 1 /elevator/perception/state
```

有效结果至少应满足：

```text
schema_version: 2
status: ok
mode: door_monitor
image_stamp: 非空且为当前时间附近
confidence.door_closed: 大于等于 0.72
```

门状态约定：

| 现场状态 | 期望输出 |
| --- | --- |
| 完全关闭 | `door_closed=true` |
| 完全打开、入口完整敞开 | `door_closed=false` |
| 半开、正在开关、遮挡或无法判断 | `door_closed=null`，`status=uncertain` |

手动检查模式切换：

```bash
rostopic pub -1 /elevator/perception/mode std_msgs/String "data: 'idle'"
rostopic pub -1 /elevator/perception/mode std_msgs/String "data: 'door_monitor'"
```

切到 `idle` 后应停止产生 API 推理请求；恢复 `door_monitor` 后应重新发布门结果。

## 9. 不运动的合并验证

在机器人保持急停或底盘不具备运动条件时，只验证感知输出：

1. 门完全关闭，确认连续输出 `door_closed=true`。
2. 门开始打开和半开时，确认不会稳定输出可通行结果。
3. 门完全打开后，确认连续输出 `door_closed=false`。
4. 遮挡相机或断开网络，确认输出变为 `uncertain/error`，而不是继续复用旧结果。
5. 机器人进入轿厢后的相机视角也必须重新做以上测试；门外正确不代表轿厢内视角正确。

当前感知频率为 `0.2 Hz`，即最多约 5 秒一次请求。控制侧还要求两次结果且跨度至少 2 秒，因此完整开门后通常需要约 5–10 秒才放行，这是正常门控延迟。

## 10. 真机低风险分阶段联调

不要第一次就录制完整流程。按下面顺序逐项通过：

1. 使用原来的“门一直开”程序再次低速验证进入、转身和退出点位。
2. 只启动感知并人工对照门状态，不运行联动程序。
3. 将机器人放在门外原点，门保持关闭，启动联动程序，确认机器人持续不动。
4. 保持人员在急停旁，再完整开门，验证机器人只执行进入和转身。
5. 机器人进入后保持门打开，确认它不会立即退出；程序应停在 `[3/5]` 等待关门。
6. 关门并等待程序进入 `[4/5]`，机器人仍应不动。
7. 再次完整开门，验证机器人退出原点。
8. 全流程通过后再正式录制。

任何一步异常都停止，不继续下一阶段。

## 12. 停止顺序

正常结束后，控制程序会向感知节点发送 `idle`。人工停止时先执行：

```bash
rostopic pub -1 /elevator/perception/mode std_msgs/String "data: 'idle'"
```

然后在控制和感知终端按 `Ctrl+C`。

重要：控制程序异常或 `Ctrl+C` 只保证不再下发后续导航目标，不保证撤销底盘已经收到的目标。机器人仍在运动时立即拍物理急停，不要依赖关闭终端停车。

## 13. 常见问题

### 13.1 机器人侧看不到 `/elevator/perception/state`

检查：

```bash
echo "$ROS_MASTER_URI"
echo "$ROS_IP"
rosnode list
rostopic info /elevator/perception/state
```

两端通常是 ROS Master 不一致、IP 不可达或防火墙阻止 ROS 动态端口。

### 13.2 一直显示 `idle`

上一次程序结束时会把模式切到 `idle`。重新启动联动程序会自动切回 `door_monitor`；手工测试时可发布：

```bash
rostopic pub -1 /elevator/perception/mode std_msgs/String "data: 'door_monitor'"
```

### 13.3 完全开门后机器人仍不动

依次检查：

- 是否已经得到两条新的 `door_closed=false`；
- `status` 是否为 `ok`；
- `mode` 是否为 `door_monitor`；
- `confidence.door_closed` 是否不低于 `0.72`；
- `image_stamp` 是否过期；
- 控制终端是否提示 schema 或时间异常。

不要通过改成单帧确认来掩盖问题。

### 13.4 门外能识别，进入后一直识别不到

这是内外视角不同造成的。检查机器人转身后的头部相机是否能看到完整门框和门缝；必要时现场调整头部姿态或感知 ROI，并重新做内侧 shadow test。

### 13.5 提示图像过期或时钟异常

检查两台机器时间：

```bash
date --iso-8601=seconds
timedatectl status
```

同步 NTP/chrony 后重新启动感知和控制程序。不要直接放宽 `max_result_age` 规避时钟问题。

### 13.6 找不到 `api`、`rospy` 或 `py_trees`

说明控制程序没有在 Kuavo 工作空间环境中启动。重新执行：

```bash
cd /home/lab/kuavo-ros-control
source devel/setup.bash
```

再从 `book` 目录启动。

## 14. 回退方法

联动失败时可以立即回到两个原有独立功能：

1. 停止 `elevator_text_main.py`，并确认机器人已通过物理急停停稳。
2. 将感知模式切到 `idle`。
3. 使用原来“门一直开”的进出程序，不运行新的联动入口。
4. 如需恢复感知工程，停止节点后把 `Demo_vlm2_kuavo_api.backup.时间戳` 恢复为原目录，再重启感知。

不要删除原来已经能运行的独立进出程序，也不要删除工程外的 API 密钥文件。
